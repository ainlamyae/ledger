# Health — Insight (AI)

[← Features](README.md) · [README](../../README.md)

## At a glance

- `/health/insight/` shows seven mode tiles in one card titled **Insight**; each mode is a page (`/health/insight/plan/`).
- Page order: From/To, question box, prompt template, data, Send to AI, answer.
- Modes: **Plan**, Wellness, Food, Micronutrient, Activity, **Protein** (formerly Protein Sources), **Pattern**.
  - **Micronutrient:** skips zero nutrients with no target; targets come from `MICRONUTRIENT_DAILY_TARGETS_JSON`.
  - **Pattern:** period averages over a length starting at Tune's `L_p`; asks what drives fat loss and a higher BMR.
- **Prompt template** dropdown shows exactly what is sent, with on-screen data as `[data shown above]`.
- Uses your own Groq key.

## Health — Insight (AI)

- One panel, seven modes, in button order: **Plan**, **Wellness**, **Food**, **Micronutrient**, **Activity**, **Protein**, **Pattern**.
- **Prompt template** — a collapsed dropdown under the mode buttons (Tune's Equations style), filled when a mode loads: the full **SYSTEM** prompt, then the **USER** message with every line already on screen (the preview lines, the table rows) folded into `[data shown above]`, and the question as `[your question, …]` (`renderInsightPromptTemplate`, `insight-panel.js`).
- **Micronutrient** (`/health/insight/micronutrient/`, formerly Micronutrients) leaves out any nutrient at 0 with no daily target (or a 0 one); a 0 against a real target stays, as a possible gap.
- **Micronutrient** (and Physique's 🧬 view) lists the Nutrition Facts lines first, in the ingredient form's order (`NUTRITION_FACTS_ORDER` / `nutritionFactsRanks`, `nutrition.js`): Calories, Fat, Saturated, Trans, Polyunsaturated, Omega-6, Omega-3, Monounsaturated, Carbohydrate, Fibre, Soluble, Insoluble, Sugars, Sugar Alcohols, Starch, Protein, Cholesterol, Sodium, Potassium, Calcium, Iron — each shown under its Canadian Nutrition Facts name (Saturated, Trans, Omega-6, Fibre, Sugars, Sodium, … instead of USDA's `Fatty acids, total saturated`, `PUFA 18:2`, `Sodium, Na`; the saved data keeps USDA's names), in the ingredient form too — then nutrients with a daily target, then the rest, each alphabetical, with a heavier rule after the Nutrition Facts lines and another above the first nutrient with no daily target.
- **Micronutrient** is the one mode NOT built on model inference — it sums each logged ingredient's real, USDA-sourced Micronutrients panel (nutrition.js's Pull Micronutrients, scaled to how much was actually eaten) and asks the AI to judge sufficiency against standard dietary reference intakes. Coverage is necessarily partial (only ingredients that have been priced contribute) — a coverage line states how many ingredients and days it's based on, and the AI is told never to read a nutrient missing from the list as a confirmed zero. Deliberately doesn't name *which* ingredients were skipped, on screen or in the prompt — a bare count is enough to convey partial coverage without inviting the model to guess at a specific food's composition from its name alone.
  - A fourth column, **Ideal / day**, next to Total (period) and Avg / day: reference daily amounts from `nutrient-targets.js`, mostly the FDA's 2016 Daily Values plus a handful of individually-sourced figures (omega-3 ALA, total water, caffeine, the indispensable amino acids, alcohol) for nutrients FDC reports that aren't on the FDA label at all. Fixed, general-adult numbers — not personalized to this user's own sex/age/body mass. Only a nutrient with a real citable reference gets one; most of what FDC reports (fatty-acid isomers, non-essential amino acids, individual sugars, sterols, carotenoids, lab-analysis fields like Ash/Nitrogen) has none, and shows `—` rather than an invented figure.
  - Once `MICRONUTRIENT_DAILY_TARGETS_JSON` (Setting) exists it is the **whole** target list, not overrides on the defaults: a nutrient deleted from it has no target. The built-in defaults only apply while the key doesn't exist, and seed it in full the first time Tune's Save writes it.
  - Overridable per-nutrient via a `MICRONUTRIENT_DAILY_TARGETS_JSON` Setting — same `{unit, amount, kind}` shape as the file's own defaults, merged on top of them, so editing one nutrient's target doesn't require replacing the whole list.
  - Rows flag a **severe or mild** gap alike (red name and left-border) only for a genuine shortfall on a "floor" nutrient (most vitamins/minerals) — the average sitting notably under its ideal. Running *over* an ideal is never flagged, on a floor nutrient or a "ceiling" one (sodium, cholesterol, saturated fat, caffeine, alcohol) alike; a ceiling nutrient's own kind is only there to keep it out of the shortfall check, since being under a limit isn't a gap.
  - The same table, thresholds and coloring drive the Physique panel's own per-day 🧬 **Micronutrients** view below — one shared `nutrientGapSeverity` (`nutrient-targets.js`), so a single day's row and this mode's period average can't disagree about what counts as a gap.
- **Nothing is computed until a mode button is clicked** — page load does no aggregation at all.
- Clicking a mode shows a preview of exactly what would be sent; Send to AI sends that same data.
- All modes prepend the same age/sex/height/body mass (with its desired target)/BMI profile block, shown on screen — Plan is the one exception, since its own PLAN INPUTS section already carries the same facts (`m`, `m_g`, `h`, `a`, `sigma`) in more detail.
- **No line repeats the date range.** Every figure in a mode covers the same window, so it's stated once by the panel's own status line rather than eight times inside the prompt. The `[only N/M days logged]` marker carries the window length wherever coverage is partial.
- **Wellness** — selected range vs. the equal-length preceding period.
- **Food** — ingredients **grouped by Group**, each group carrying its own ingredient count and calorie/protein totals.
  - Groups are ordered by calories; `Unclassified` always sinks to the bottom and is flagged to the model as not a food group.
  - The preview table groups identically.
  - Four more columns after Protein — **Fiber, Fat, Carbohydrate, TEF** — this ingredient's own typed figure on its `Nutrition` row when it has one, else read off its pulled 🧬 Micronutrients panel (Fiber/Fat/Carbohydrate) or the Atwater/TEF-share formula (TEF), scaled to its range total (`estimateMacrosForFoodRow`, `micronutrient-insight.js`) — same typed-over-estimated resolution and per-ingredient math the Nutrition table and Physique breakdown use, just aggregated over the picked range instead of one row/day. Blank (`—`) on an ingredient with neither a typed figure nor Micronutrients pulled, never a claimed zero. TEF alone is sent to the model too (`~X kcal TEF` per ingredient line, `estimateTefForFoodRow`) — Fiber/Fat/Carbohydrate are shown for reference but not sent, since the prompt is a plain-text list, not this table.
  - Where the Nutrition row has no figure for one of these — or there is no Nutrition row at all (the Unclassified foods) — the column falls back to the logged Breakdown's own Fiber/Fat/Carbohydrate/TEF, summed over the range (`breakdownMacros`, `aggregateFoodIntake`), so a figure Calculate saved never shows as —.
  - **The table closes with Total and Avg/day rows** (`renderFoodInsightPreview`, `food-insight.js`) — Total sums every ingredient's Calories/Protein/Fiber/Fat/Carbohydrate/TEF (across the whole table, not per group); Avg/day divides each of those by how many days actually have Calculate-derived data in the picked range (`countMicronutrientLoggedDays`, the same divisor the Micronutrients mode's own per-day figures use), not the range's calendar length, so a partially-logged window isn't understated. Either row reads `—` on a column nothing in the table could measure, same convention as the per-ingredient cells above.
- **Activity** — rep volume vs. the previous period, a routine-activity summary, and a per-muscle-group breakdown sorted most-neglected-first.
  - Each muscle group carries **the exercises that built it** — every movement logged against it in range and its total reps, heaviest first. The model is told these are the movements the user actually has access to, so recommendations name them instead of inventing lifts.
  - Non-resistance types (a walk, a swim) are **summarised, not listed per day** — one row each with days logged and the range/average of minutes, kcal and steps. Repeating a daily walk for every date buried the sessions that differ.
  - The split is by content, not by name: a type is routine when nothing logged under it carries reps.
  - Minutes are **net active time**, not session wall-clock. The system prompt says so explicitly and tells the model to judge training by rep volume and muscle coverage — an 8-minute resistance session is a real one, and "spend more minutes" is never the advice.
- **Protein** (`/health/insight/protein/`, formerly Protein Sources) — reuses `computeProteinRotationRows` (Protein Source Rotation, below) directly, so this mode's figures can never disagree with that chart: every tracked ingredient's own target share of the protein target vs. the share actually eaten in range, grouped by Group, largest shortfall first.
  - The target percentages are the user's own rotation plan, not a nutritional prescription — the system prompt tells the model to judge how well actual eating matched the mix, not to second-guess the mix itself.
- **Plan** — the only mode that reads the app's **settings** rather than the day log: it sends the Tune's whole plan and asks whether it's feasible.
  - Three blocks, **PLAN INPUTS first**: the person's own numbers (including which figure is pinned as body mass falls), then the published identities (the playground's own `FORMULA_EXPRESSION`, so screen and prompt can't diverge), then the substituted arithmetic — at **full Tune (Tune) parity**, same figures in the same order: `LBM → BMR (Mifflin & Katch) → BMR_cal → E_act → D → E_in → TEF → Δm → A → B → m∞ → t → BMI_des → Δm% → D_bmr% → BMR_adp → m∞_adp → m_musc → m_gly → ΔM_gly → P_min/max → F_min/max → G_min/max → C_min/max`. Every figure is computed in `gatherPlanSnapshot` by the same `wellness-math` functions (off the same rounded intake) the playground uses, so the two can't quote different numbers.
  - Computed from `Setting` + the smoothed body mass (`planBodyMassKg`), **not** the playground's input boxes: the modal may never have been opened, and the saved values are what the app actually runs on. Same functions as the playground and the charts (`calorieTargetDetail`, `maintenanceAffineCoefficients`, `projectTargetDays`, `boerLeanBodyMassKg`), so all three describe one plan.
  - The prompt states which BMR equation is in force, quotes the raw body-mass reading alongside `m̄` (so the model doesn't read the difference as an inconsistency), spells out the `(1 − f)` divisor only when digestion is being counted, and carries the adaptation caveat — `BMR_adp` by the arrival date and the plateau it implies — next to the `m_inf` it qualifies.
  - A fourth block carries **Wellness' own aggregation** for the selected range, unchanged — feasibility is a question about the gap between the plan and the logging, so the model gets both. A plan whose activity burn assumes daily movement that isn't being logged is arithmetic, not a plan.
- **Pattern** (`/health/insight/pattern/`, formerly Patterns) — the BMR_cal Periods table for the picked range (`computeBmrCalibration` with the To date as its end), widened with each period's averages: `Period, m, Δm, ΔM, BMR_mif, BMR_kat, BMR_cal, BMR_adp, SD, TEI, Protein, Dietary Fiber, Fat, Carbohydrate, TEF, AEE, Cardio, NEAT, Strength, D, Offset`. The AI is asked which habits line up with the most negative ΔM (more fat lost) and the highest Offset (a higher real BMR).
  - Period length is an editable **period length** row above the table (Tune's row style, without the `L_p` symbol), starting at Tune's L_p (`patternChunkDays()`: Tune's box, else the saved `BMR_CALIBRATION_PERIOD_DAYS`, default 10); a blank box falls back to it — it drives `computeBmrCalibration`'s own chunk size, so the periods table, the data prompt ("PERIODS (N-day averages...)") and the system prompt ("self-tracked N-day periods") all read off the one typed value and can't disagree about it.
  - Cardio/NEAT/Strength split each day's AEE by activity category (`physiqueActivityByCategory`); a logged day with none of a type counts as 0.
  - Periods with no logged day are shown greyed out and left out of the prompt.
  - The system prompt names what to check: `E_in` against BMR, the weekly rate against ~0.5-1% of body mass, whether τ is actually being done, whether protein is inside the band at that deficit, and whether `t` agrees with the measured trajectory. Sections are **Verdict / What works / Risks / Do this / Avoid this**, with the last two as numbered lines naming the input responsible.
  - Missing profile settings produce a prompt that says so plainly and still sends the logging, rather than a plan full of nulls.
- Reports render as plain text without `innerHTML` (untrusted model output) and persist per mode.
